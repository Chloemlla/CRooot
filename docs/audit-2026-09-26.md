## CR-01　`checkBuildFieldCoherence` 对 build id 做严格相等，vivo 的厂商后缀直接触发 HIGH

- **编号**：CR-01
- **文件**：`sdk/src/main/java/com/juanma0511/rootdetector/detector/RootDetector.kt`（`crossPartitionFingerprintMismatch`，`hardMismatch` 里的 `build.buildId != system.buildId`）
- **类型**：判据过严（跨分区指纹比较）
- **现场取值**：
  - `ro.build.fingerprint` = `vivo/PD2426/PD2426:16/BP2A.250605.031.A3_V000L1/compiler260331112521:user/release-keys`
  - `ro.system.build.fingerprint` = `vivo/PD2426/PD2426:16/BP2A.250605.031.A3/compiler260331112521:user/release-keys`
- **根因**：`parseFingerprint` 把 build id 解析为 `BP2A.250605.031.A3_V000L1` / `BP2A.250605.031.A3`；`hardMismatch` 用严格相等比较两者，于是厂商的 per-shipment 后缀 `_V000L1` 被当成「核心构建字段不一致」。同文件的 `compatibleIncremental()` 已经对 `_` 后缀和前缀关系做了容错，buildId 却没有。
- **症状**：`build_field_coherence`（HIGH）在 stock vivo 上恒命中 → `kkndRoot.isRooted = true` → 宿主判 root。
- **修复**：新增 `compatibleBuildId()`（相等 / 互为前缀 / 去掉 `_` 后缀后相等），`crossPartitionFingerprintMismatch` 用它替换严格相等；`runtimeFingerprintMatches()` 保持严格（它比的是 `Build.FINGERPRINT` 与同一批 prop，不应放宽）。
- **回归**：`sdk/src/test/java/com/juanma0511/rootdetector/detector/CompatibleBuildIdTest.kt` 钉住现场那对指纹。

## CR-02　`rootPaths` 里的裸 `/debug_ramdisk` 让 `bootLooksTrustedLocked()` 在 stock Android 11+ 上恒为 false

- **编号**：CR-02
- **文件**：`sdk/src/main/java/com/juanma0511/rootdetector/detector/DetectorTrust.kt`（`hasExplicitRootArtifacts()` 的首行 `rootPaths.any { File(it).exists() }`）、`HardcodedSignals.kt`（`rootPaths` 首项 `/debug_ramdisk`）
- **类型**：判据把挂载点当成 root 痕迹
- **现场取值**：`ls -ld /debug_ramdisk` → `drwxr-xr-x 2 root root 27`，目录**为空**，且 `/proc/mounts` 里没有任何 `/debug_ramdisk` 挂载项。
- **根因**：`/debug_ramdisk` 是 Android 11+ 的 debug ramdisk 挂载点，user build 上常只剩一个空目录。`hasExplicitRootArtifacts()` 用「目录存在」判「有 root 痕迹」，于是任何 stock 设备都返回 true → `bootLooksTrustedLocked()` 恒 false → 所有依赖 `trustedLocked` 的护栏（`hasRootMountSignal`、`isSuspiciousDeletedOrMemfdMap`、`checkWritablePaths`、`checkMountInfoConsistency`、`checkMemfdArtifacts`）在 stock 设备上全部失效。
- **修复**：新增 `STOCK_MOUNT_POINTS = setOf("/debug_ramdisk")`，`hasExplicitRootArtifacts()` 的目录存在性判断跳过它；真正代表 root 的 `/debug_ramdisk/.magisk`（`magiskPaths`）与 `/debug_ramdisk/su`（`suPaths`）仍在 `rootPaths` 里，照旧会被判到。挂载表/内存映射文本里的 `/debug_ramdisk` 匹配保持不变（只有真的挂了/映射了才会出现）。

## CR-03　`rootPackages` 把免 root 的 LSPatch 列进 HIGH 根管理器清单

- **编号**：CR-03
- **文件**：`sdk/src/main/java/com/juanma0511/rootdetector/detector/HardcodedSignals.kt`（`rootPackages`）；消费点 `RootDetector.checkRootPackages()`（HIGH `root_packages`）、`RootDetector.checkPackageManagerAnomalies()`（HIGH `pm_anomalies`）
- **类型**：分类错误（同一包在两份清单里分属 HIGH 与 WARNING）
- **现场取值**：设备上真实安装了 `org.lsposed.lspatch`（`/data/app/~~HJYGbLxPzDQphH_l5yGDUg==/org.lsposed.lspatch-phe9iXWbE-Nr4uvdq2oepQ==/base.apk`）。
- **根因**：`org.lsposed.lspatch` 同时出现在 `rootPackages`（→ HIGH）与 `patchedApps`（→ WARNING `patched_apps`）。LSPatch 是**免 root** 的 Xposed 方案（LSPosed 的 patch 变体），把它当 root 管理器会让任何装了 LSPatch 的设备被判 root。
- **修复**：从 `rootPackages` 移除该条目，保留 `patchedApps` 里的 WARNING 归类。
- **回归**：`sdk/src/test/java/com/juanma0511/rootdetector/detector/HardcodedSignalsTest.kt`。
- **未一并处理（另开一轮）**：`rootPackages` 与 `patchedApps` 还有 14 个重叠条目（`org.lsposed.manager` / `de.robv.android.xposed.installer` / `com.tsng.hidemyapplist` / `com.fox2code.mmm` / `com.estrongs.android.pop` / `rikka.safetynetchecker` …）。其中 `com.estrongs.android.pop`（文件管理器）与 `rikka.safetynetchecker`（检测工具）看起来同样不该是 HIGH，但「装了 Xposed/LSPosed 管理器算不算 root 证据」需要单独定标，不在本次范围内擅自改。

## CR-04　`checkADBNetwork` 把 `service.adb.tcp.port=5555` 直接判 HIGH

- **编号**：CR-04
- **文件**：`sdk/src/main/java/com/juanma0511/rootdetector/detector/RootDetector.kt`（`checkADBNetwork`）
- **类型**：判据只看 prop、不看端口是否真的在监听
- **现场取值**：`getprop service.adb.tcp.port` → `5555`；同一时刻 `/proc/net/tcp` 里**没有** 5555 的 `LISTEN` 记录（用户只用 USB 连接）。vivo 打开 USB 调试即写入该 prop。
- **症状**：`adb_network`（HIGH）在开发者设备上恒命中 → 再叠加一条「root」判据。
- **建议改法**：prop 降级为上下文（WARNING），HIGH 只在 `/proc/net/tcp{,6}` 里真的观察到 5555 `LISTEN` 时给出。
- **状态**：**未修**。这是安全语义取舍（放宽一条 ADB 判据），需要仓库所有者定标后再动，本次只记录。

## CI-01　`android-actions/setup-android@v3` 已失效，CRooot 的 CI 自 2026-08-02 起无法完成

- **编号**：CI-01
- **文件**：`.github/workflows/android-sdk-ci.yml`、`.github/workflows/android-sdk-release.yml` 的 `Set up Android SDK tooling` 步骤
- **类型**：CI 外部漂移（与代码改动无关）
- **现场**：
  ```
  [command]/usr/local/lib/android/sdk/cmdline-tools/16.0/bin/sdkmanager tools
  Warning: Failed to find package 'tools'
  Error: The process '...sdkmanager' failed with exit code 1
  ```
- **根因**：`android-actions/setup-android@v3` 会安装 legacy 的 `tools` 包，而 Google 已把它从 SDK 仓库移除。该动作在**任何 Gradle 步骤之前**就失败。归因：`main` 上最后一次成功是 `f194255`（2026-08-02），此后无人推过 `sdk/**`，所以这六周的失败与本次代码改动无关。
- **修复**：删掉该动作，改为一个只负责定位 `cmdline-tools` 并把 `sdkmanager` 加进 `GITHUB_PATH` 的步骤（runner 镜像本来就带 cmdline-tools，后续 `Install exact Android SDK packages` 步骤负责装精确版本）。两个 workflow 同步修改。

## CI-02　`CRooot/sdk` 的单元测试源集从未编译过，现在也编不过 —— 无法为 CR-01/CR-03 加回归测试

- **编号**：CI-02
- **文件**：`sdk/src/test/java/com/eltavine/duckdetector/features/tee/data/soter/SoterCapabilityProbeTest.kt`、`.github/workflows/android-sdk-ci.yml`
- **类型**：测试源集失效（从未被 CI 编译过）
- **现场**（把 `:sdk:testDebugUnitTest` 加进 CI 后暴露，6 个错误全部在这一个文件）：
  ```
  e: SoterCapabilityProbeTest.kt:76:9  Name contains illegal characters: :.
  e: SoterCapabilityProbeTest.kt:102:9 Name contains illegal characters: :.
  e: SoterCapabilityProbeTest.kt:128:9 Name contains illegal characters: :.
  e: SoterCapabilityProbeTest.kt:190:35 None of the following candidates is applicable:
  e: SoterCapabilityProbeTest.kt:190:35 No value passed for parameter 'p0'.
  e: SoterCapabilityProbeTest.kt:198:20 / :202:20 同上
  > Task :sdk:compileDebugUnitTestKotlin FAILED
  ```
- **根因**：
  1. 三个反引号测试名含 `:`（`safety fix: never removes ...`）——Kotlin 2.4 已把这种名字判为非法。
  2. `SoterCoreResult()` 无参构造在当前解析到的 Soter 版本上不存在（`No value passed for parameter 'p0'`）。该类型来自 `soter-wrapper:2.0.7` 的**传递依赖**（`soter-wrapper` 自己的 AAR 里只有 `com/tencent/soter/wrapper/**`），测试写的是另一个版本的 API。
  3. 之所以一直没人发现：`android-sdk-ci.yml` 只跑 `:sdk:lintRelease :sdk:assembleRelease`，**不编译也不运行 `sdk/src/test`**。
- **修复**（`e41660a` + `92f9087`）：
  1. **查清 Soter 真实 API（不猜）**：从 JitPack 取 `soter-core-2.0.7.aar` 解包后 `javap`：`SoterCoreResult` 只有 `(int)` 与 `(int, String)` 两个构造，无无参构造；`isSuccess()` 的实现是 `errCode == 0`，`SoterErrCode.ERR_OK == 0`。因此 3 处 `SoterCoreResult()` 改为 `SoterCoreResult(SoterErrCode.ERR_OK)`，语义与原来的「成功」一致。
     **同时更正本文档早先的判断**：原文写「`SoterCoreResult()` / `SoterSessionResult()` 无参构造都不存在」。实测 `SoterSessionResult` **有**公开无参构造，`SoterSessionResult().apply { resultCode = 0; session = 12345L }` 原样保留即可，无需改动。
  2. 三个反引号测试名去掉 `:`。
  3. `android-sdk-ci.yml` 加回 `:sdk:testDebugUnitTest`。任务名**不是** `testReleaseUnitTest`：AGP 9 起 `android.onlyEnableUnitTestForTheTestedBuildType` 默认 `true`，只给被测试的 build type 创建单测组件。
  4. 恢复 `9287c03` 删掉的回归测试 `sdk/src/test/java/com/juanma0511/rootdetector/detector/CompatibleBuildIdTest.kt`（钉 CR-01）与 `HardcodedSignalsTest.kt`（钉 CR-03）；恢复前先把 `HardcodedSignals` 的混淆清单解出来（Base64 解码后逐字节 XOR `0x37`），确认断言对得上实际出厂数据，而不是照着混淆串猜。
  5. 修 `CRoootLocalReportTest` 的 NPE：`CRoootLocalReportMapper.environment()` 读 `Build.SUPPORTED_ABIS`，而 AGP 的 **mockable android.jar 会把带非常量初始化器的 static final 字段置为 null**（`isReturnDefaultValues = true` 只影响方法桩，不影响静态字段），`firstOrNull()` 因此 NPE。该分支依赖 Android 运行时静态、在纯 JVM 单测里不可达，故把该测试改为 `includeEnvironment = false`，并补一条断言钉住由此产生的 `Environment metadata was intentionally omitted.` limitation，避免覆盖面的变化是静默的。
- **验证**：`92f9087` 的 CI run `36226761588` 绿，`:sdk:testDebugUnitTest` 实跑 1m49s、`BUILD SUCCESSFUL`（不是 `UP-TO-DATE`/`FROM-CACHE`）；两个快照比对稳定，且 `Android SDK Release` 是 `workflow_dispatch` 不随 push 触发，无迟到 job。对照前一版 `e41660a` 的 run `36226317398` 报 `29 tests completed, 1 failed`——即这 29 个测试（含恢复的 CR-01/CR-03 回归）现已全部通过。
- **遗留缺口（未修）**：`CRoootLocalReportMapper.environment()` 这一分支仍无自动化覆盖（只能在真机上跑到）。CR-04 与 14 条清单重叠条目的「行为」同样没有自动化回归，理由见各自条目。
- **附带收获**：CI-01 修好的 `android-sdk-release.yml` 本轮实跑发布成功（`1e8f806` → `crooot-sdk:0.1.1`），确认这条发布链路可用。
